# 登录、注册与 MFA

这套工作台**默认不对外开放**：所有接口都要登录，登录必然经过 MFA（TOTP）。
本文写清它由什么构成、每一步的取舍是什么、以及出问题时该看哪里。

## 一、为什么是"注册即强制绑定 MFA"

数据在这一侧：库里有**明文保存的交易所凭据**（见 [EXCHANGES.md](EXCHANGES.md)）。
拿到这个库就等于能下单，所以入口这一关不能只有口令。

因此没有"关掉 MFA"这个选项。账号上只有两种状态：

| 状态 | `users.totp_secret` | 登录时会怎样 |
|---|---|---|
| 未绑定 | `NULL` | 先扫码绑定，绑完即完成这次登录 |
| 已绑定 | Base32 密钥 | 直接输验证器里的六位码 |

少一个开关就少一条绕过路径——"关闭 MFA"这种字段最容易被随手打开，
而它恰恰是这类系统最常见的洞。

## 二、流程

```
注册                          登录
────                          ────
① POST /api/auth/register/code   ① POST /api/auth/login        （邮箱 + 口令）
   邮箱 → 六位码（10 分钟内有效）      → 已绑定：{ status: "mfaRequired", challengeId }
② POST /api/auth/register          → 未绑定：{ status: "mfaBindingRequired",
   邮箱 + 码 + 两次密码                        challengeId, secret, otpauthUri }
   → 204（**不签发会话**）         ② POST /api/auth/mfa/verify   （六位码 → 会话 Cookie）
                                   或 POST /api/auth/mfa/bind   （扫码后输码 → 绑定 + 会话）
```

几个刻意的设计：

- **注册不签发会话**。少一条"注册即登录"的捷径，就少一个能绕过第二个因子的入口。
- **登录第一步永不签发会话**。它的产出只有"下一步做什么"，前端据此决定显示输码框还是二维码。
- **口令错与账号不存在回同一句话**：分开说等于免费回答"这个邮箱注册过没有"。
- **未绑定时把密钥返回前端，由前端画二维码**。服务端只给 `otpauth://` 那串 URI——
  密钥不必经过任何第三方二维码服务，服务端也不必引一个画图库。

## 三、算法与存储

| 项 | 取值 | 说明 |
|---|---|---|
| MFA | TOTP：RFC 6238 + RFC 4226，HMAC-SHA-1，6 位，30 秒步长，±1 步容差 | SHA-1 是刻意的：验证器 App 默认凭证等价于它，换 SHA-256 会有相当一部分 App 算出的码永远不对 |
| 密钥 | 20 字节随机，Base32（RFC 4648） | RFC 4226 §4 的建议长度，也是 App 的默认 |
| 口令 | PBKDF2-HMAC-SHA256，210k 轮，16B 盐，32B 输出 | 编码成 `pbkdf2-sha256$迭代数$盐$哈希` 单列存储，将来可调迭代数而不影响老口令 |
| 注册验证码 | 6 位数字，10 分钟有效，≤5 次尝试，60 秒重发冷却 | 一百万种可能，没有尝试上限等于把码送出去 |
| 登录防爆破 | 同邮箱 5 次失败锁 15 分钟 | 按邮箱而不是按 IP：只监听本机，IP 没有区分度 |
| 会话 | Cookie（`poolpilot_session`），HttpOnly + SameSite=Lax + 7 天滑动过期 | 前端拿不到它，因此没有"令牌存哪儿"这个决定 |
| 临时状态 | 内存缓存（`IMemoryCache`） | 验证码、登录挑战、失败计数都不落库：重启即失效反而是想要的 |

**时间步的用法**（`TotpGenerator.Verify`）：只拒绝**比上次更旧**的时间步。
同一个时间步可以再用——绑定时用掉的正是当前这一步，紧接着重新登录会拿同一个码进来，
按"必须严格更新"判就会在注册完立刻告诉使用者"验证码不正确"，而他只能干等 30 秒。
代价是一个码在它自己的窗口内（≤90 秒）可被重复提交：对本机工具，这个代价换掉那半分钟的困惑是值得的。

## 四、通知（注册验证码怎么发出去）

验证码由「通知」页里配置的**通道**发出。三块内容：

- **提供商**（通道）：目前只有邮箱（SMTP）。**可以配多条**（内部用一个、对外用一个），
  参数含主机、端口、登录名、口令、发件人。口令是**明文落库**的，与交易所凭据同一条约定：
  库在本机、已 gitignore，而"密钥与密文同库"等于没防；界面上只回显尾号。
- **样板**：每类通知一条，含主题与正文、以及**由哪条通道发**。
  多个同类通道并存时，"发注册码用哪个"就由样板上的选择回答，不再另设"默认通道"那种全局开关。
  正文里的占位符：`{code}`、`{email}`、`{minutes}`——其中 `{code}` **必须保留**，
  界面与后端都会拦下删掉它的保存（否则收信人看不到码，而系统这边照样报"发送成功"）。
- **记录**：每一次投递都留一条，成功与失败都留。存的是**快照**（通道名、类型、渲染后的主题与正文），
  所以通道日后改名或删除，这条记录仍能说清"当时用的是谁、发了什么"。验证码只在邮件里出现过一次，
  事后要回答"到底发出去没有"，只能靠它。

**没有可用通道时不会假装成功**：内容写进服务端日志（并打 Warning 提示"仅限本机调试"），
接口返回 `delivered: false` + 一句能照着做的话（"去「通知 → 提供商」配一条"），
注册页把它显示成一个停留更久的警告。
发送失败（口令过期、发件人未验证、端口被拦）**不是 5xx**：结果里带着 SMTP 的原话，
因为它正是使用者唯一需要看到的东西。

### 配置 QQ 邮箱的例子

QQ 邮箱用**授权码**而不是登录密码（在 QQ 邮箱设置 → 账户里生成）：

| 字段 | 值 |
|---|---|
| 主机 | `smtp.qq.com` |
| 端口 | `587`（STARTTLS） |
| 登录名 | 完整邮箱地址 |
| 口令 | 授权码 |
| 发件人地址 | 同一个邮箱地址（QQ 要求发件人即账号） |

> 465 端口那种"隐式 SSL"自带的 `SmtpClient` 连不上——它只会"先明文连接、再用 STARTTLS 升级"。
> 各家邮箱都同时提供 587，换端口即可。

## 五、出问题了看哪里

| 症状 | 先看 |
|---|---|
| 点了"发送验证码"但没收到 | 「通知 → 记录」里那一条：`仅写日志`／`失败`（失败原因就是 SMTP 的原话）／`已发出` |
| 验证器算的码总是不对 | 手机时间是否自动同步；密钥是否被手机输入法改动（用界面上的复制按钮重来一次） |
| 换手机 / 验证器丢了 | **没有找回流程**（见下） |
| 会话莫名失效 | Cookie 7 天滑动过期；服务端重启也会让挑战与验证码失效（它们只在内存里） |

## 六、首次启用时的先有鸡还是先有蛋

**注册要验证码 → 验证码要一条通道 → 通道的配置在登录之后**——这三件事绕成一个环，
而库里还没有任何账号时，这个环是闭合的。当前只有两条出路：

1. **从服务端日志里取码**（不配任何通道时的降级路径）：跑 API 的那个终端里找
   `你的注册验证码是：\d{6}`。这是默认状态下唯一不需要动数据库的办法。
2. **先手工插一条通道再注册**（本文档第一节那种配置，直接写 `notification_providers`
   并让 `registration_code` 样板指向它）。适合"通道参数早就在手上"的人。

**待办**：加一个「首次初始化」界面——在还没有任何账号时，允许先配通道（或先用日志里的码）
再进入注册，把这个环打开。在那之前，上面的两条就是全部办法。

## 七、已知边界（刻意不做）

- **没有找回密码、没有改密码、没有解绑 MFA**。这三件事都需要"证明你是你"的额外通道
  （备用邮箱、恢复码、管理员介入），而那套东西本身又是一个要设计、要审计的面。
  当前的做法是：**忘了就删掉那条账号重来**——
  ```bash
  sqlite3 data/poolpilot.db "delete from users where email = 'you@example.com';"
  ```
  这是一台只监听本机的工作台，这么处理是诚实的；真要多用户，这一节必须先重做。
- **没有角色与权限**：一个账号看到的就是全部。
- **MFA 的密钥与 SMTP 口令都是明文落库**（与交易所凭据同一档）。库文件已 gitignore，
  但备份与拷贝要自己当心。
- **挑战与验证码只在内存**：多实例部署不成立（本项目是单进程单体）。
