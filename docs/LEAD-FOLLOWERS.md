# 带单员与跟单员

这份文档说明 PoolPilot 的核心职责划分：**谁在观察池子，谁在下场跟单**。两者的生命周期完全独立，这是整套设计的地基。

---

## 1. 两个角色

| | 带单员（LeadTrader） | 跟单员（Follower） |
|---|---|---|
| 是什么 | 某个公共资金池的**观察者** | 带单员信号的**订阅者** |
| 身份 | 池的账户索引（一个池最多一个） | 自增 Id（一个池可以挂多个） |
| 干什么 | 订阅 WS 持仓/成交频道，差分出信号，落库并广播 | 收信号，按自己的本金与模式决定跟不跟、跟多少，落纸面账 |
| 生命周期 | **与有没有人跟无关**：实例在就在观察 | 与观察无关：创建/暂停/删除都不影响池子被盯着 |
| 界面 | 「带单员」页 | 「跟单」页 |

一句话：**带单员产出信号，跟单员消费信号。** 两者之间只有信号这一条通道。

## 2. 为什么必须拆开

拆分之前，"订阅哪些池"是由**活跃跟单账户**推出来的：取消跟单等于顺手把观察也关掉。三个后果：

1. 池子后来的动作再没人记录——而那些信号恰恰是"先观察一段时间再决定跟不跟"的唯一依据，事后补不回来（当时的盘口已经不在了）。
2. 新配置的跟单员没有历史可看，只能等以后的动作。
3. 一个池只能有一个跟单账户（主键就是池索引），不同本金各跟一份做不到。

现在：订阅集合 = **带单员集合**，与跟单员集合完全正交。取消跟单只是把订阅者从带单员身上摘掉一个。

## 3. 信号

```csharp
public sealed record LeadSignal(PoolEvent Event, string PoolName, UsdAmount PoolEquity);
```

- `PoolEvent` 复用已有的仓位变化事件：`Open/Increase/Reduce/Close/Flip` + 市场 + 前后仓位 + 参考价 + 时刻。
- 额外带**池名**（记账与界面要可读）与**池子权益**（规模比例的分母）。
- 带上权益是关键：跟单员因此**只凭信号就能算出目标仓位**，不必回头再取一次池子状态。

## 4. 触发模型（谁会真的动起来）

| 触发 | 谁调用 | 作用 |
|---|---|---|
| **WS 持仓推送**（主路径） | `LeadTraderHostedService` → 注册表 | 池子一动就差分出信号、落库、广播、分发给订阅者。这是"事件驱动"那条路 |
| **心跳**（15 秒） | 同上 | 兜底：与库同步（新配置的带单员/跟单员上线）、让订阅者按最近快照对齐 |
| **连接断开期间** | 同上 | 退回 REST 拉快照。推送不可用时，跟单员不至于静止到重连为止 |
| **配置写完** | Api → `ILeadTraderSync` | 立刻同步一次，让"暂停/恢复/新建"当场生效，而不是等下一次心跳 |

一条实测出来的事实决定了上面必须有"心跳"这一路：**持仓频道只在真正变化时推送**，池子不动时一条都不推。所以"没有事件"与"我落后了"光看推送是分不开的。

## 5. 跟单员的两种入口

```csharp
public interface IFollower
{
    Task OnSignalAsync(LeadSignal signal, PoolSnapshot state, ...);  // 池子刚动了一下
    Task CatchUpAsync(PoolSnapshot state, ...);                      // 我现在应该和池子一样
}
```

- `OnSignalAsync` 只是触发，对账时照样覆盖**全部市场**：差额为 0 的市场既不该取盘口也不该写记录，所以多对几个市场的代价是零，而漏掉一个市场的代价是长期偏离且界面看不出来。
- `CatchUpAsync` 用于订阅瞬间、断线恢复、服务重启、配置变更。它按**当前状态**建仓，不重放历史成交——"我来晚了"时这是唯一正确的做法，也与真实跟单一致（跟的是领单人的现有仓位，不是他的开仓价）。

## 6. 纸面账的口径

- 规模：`目标仓位 = 池子仓位 × (本金 ÷ 池子权益)`，再量化到交易所步长。
- 保证金沿用**源池的初始保证金率**：成交时把源池在该市场的 `initial_margin_fraction` 记进流水，
  多次加仓按成交名义额加权；`保证金 = 持仓价值 × 保证金率`，`投资回报率 = 未实现盈亏 ÷ 保证金`。
  旧流水没有这一列时退回源池当前值；源池已无该仓且旧流水也没记，则 ROI 显示 `—`，不拿名义价值冒充。
- 清算价按**全仓口径**算：只让这一笔价格变动，解 `账户权益 = 维持保证金要求`。
  维持保证金率取合约规格的 `maintenance_margin_fraction`；任一在仓市场缺价或缺维持率时不给清算价，
  少算占用会把清算价推远，是危险的方向。
- 跳过要记，而且要**按"市场 + 原因 + 当时的池仓"去重**：本金不足时同一个跟不动的目标每 15 秒会被重算一次，不去重会把台账淹掉。
- 改本金**清空该跟单员的流水**：本金是规模比例的分母，两种本金下的历史混在一条曲线上不对应任何真实实验，却会被读成"跟单业绩"。

## 7. 边界与已知限制

- **一个跟单员只订阅一个带单员**。多源合成需要冲突消解规则（两个带单员给出相反信号时听谁的），不在范围内。
- **暂停带单员不自动平仓**：暂停只停止产生新信号，跟单员的仓位保持不动。平仓是交易决策，必须由人做。
- **停止带单员前必须先清空订阅者**：删掉观察者而把订阅者留在原地，会造出"看着在跟随、其实永远收不到信号"的状态，而界面上它跟正常运行一模一样。
- **退订帧未验证**：WS 协议里没有实测过退订帧，所以暂停的池只是"不再处理它的帧"，频道仍连着。宁可多收几帧，也不猜协议。
- **实盘模式只落字段**：`CopyMode.Live` 在实体与 DTO 上就位，执行侧没有签名器（纯 .NET 环境签不了 Lighter 的订单），配置接口会明确拒绝。

## 8. 数据库

| 表 | 主键 | 说明 |
|---|---|---|
| `lead_traders` | 池账户索引 | 存在即被观察。池名在此落一份快照（池改名/下线后历史仍可读） |
| `followers` | 自增 Id | 订阅的带单员、本金、模式、启用状态；另有 `is_public` / `owner_user_id` / `owner_credential_hash` / `label` 四条可空列服务公开页（工作台建的行四条都留空，见 [PUBLIC-PAGES.md](PUBLIC-PAGES.md)） |
| `follower_fills` | 自增 Id | 该跟单员的动作流水（成交 + 跳过），键是 `follower_id`；`InitialMarginPercent` 记成交时源池的保证金率（旧行为空） |
| `follower_equity_points` | 自增 Id | 盯市权益点 |
| `pool_events` / `copy_fills` | 自增 Id | **池子级**的观测产物，键仍是池索引——它们记录的是池子发生了什么，与谁在跟无关 |

从"纸面账户"（主键 = 池索引）迁到"跟单员"（自增 Id）曾经是一次性数据迁移：账户搬成跟单员、流水与权益点按 `池索引 → 跟单员 Id` 改键、旧表删除。它在开发库上已经执行完毕，迁移代码已按"代码只保留最新状态"移除——`DatabaseSchemaInitializer`
现在只管建表、补表，以及**补库里缺的可空列**（公开页那四条就是补上去的），
不搬历史数据、也不改任何已有列的语义。

## 9. 实盘跟单的语义：只跟动作（2026-10-07 改）

**跟单跟的是池子的动作，不是池子的持仓状态。** 这条区别决定了"什么时候会有单子出去"：

| 时机 | 会下单吗 | 目标怎么来 |
|---|---|---|
| 池子发生买卖（信号） | ✅ | 目标 = 我方当前 + **这次动作的幅度** × 比例 |
| 挂载 / 恢复 / 改配置 | ⚠️ 会，但**过价格门** | 目标 = 池仓 × 比例，且只在现价不差于池子开仓价时补 |
| **心跳（15 秒）** | ❌ **不下单** | 只做体检：算出偏差、记日志 |
| 断线重连 | ❌ 不下单 | 同上（断线期间漏掉的动作不会自动追） |

### 为什么改

改之前是**状态跟踪**：目标 = 池仓 × 比例，任何偏离都在 15 秒内被纠正。它的问题是
"池子没动，系统也在动"——使用者在界面上手动平掉一笔仓位，下一次心跳就把仓位买回来了；
手动开的仓也会被按比例"修回去"。实测出现过：手动平仓 11:22:58，11:23:30 又被重建。

### 代价（必须知道）

**漏掉的一次不会自动补。** 断线、重启、被交易所最小下单额挡住——这些情况下的动作就是没跟上，
系统**不会**替你去追。为了不让偏离变成静默的，心跳会把它算出来并记进日志：

```
跟单员 10 存在跟踪偏差：BTC 按比例应有 0.000045、实际 0.000000
（名义 3.94 vs 0.00 USDT）。偏差不会自动修（只跟动作）……
```

同一标的、同一池仓数量只报一次（池子再次动过才会重新报）。另外每一条没跟上的动作在
**实盘流水**里都有一行 `skipped` 带原因，所以"为什么我比池子少"，从流水上能查。

### 来晚了为什么不追

挂载对齐保留着（否则新跟单员会一直空仓等池子下次动作），但每一笔都过价格门
（`LiveCatchUpRule`）：**现价必须不差于池子的开仓价**。池子在 P₀ 建的多仓、现价已涨到 P₁，
这时补上去等于买得比它贵——之后每一分波动都要先填平这个差价，那不叫跟单，叫接盘。
不满足时记一笔 `skipped`，原因写着差了多少个百分点（`NotWorthIt`）。

判据用**价格**（池子开仓价 vs 我们的成交价），不用池子账户的盈亏百分比：后者按保证金算、
受杠杆影响，而这里要比的是"我能不能拿到比它更好的入场价"。跨场所的价格有几点基差，
所以这条规则的精度就是几个基点——它挡的是"已经涨了一截还去追"，不是"差一个基点也要卡住"。

### 纸面为什么不一样

纸面跟单**照旧在心跳时对账**（贴着池子）。它回答的问题是"一直跟着它、账会变成多少"，
漏跟会让收益率失真；而实盘回答的是"我该在什么时候真的下单"，那里池子没动就不该有单子出来。
两者的分工写在 `IFollower.CheckDriftAsync` 的注释里。

### 流水的触发者

`signal`（池子动作）/ `align`（挂载对齐）/ `manual`（人在界面上手动下的）。
复盘时"这一笔是谁的决定"必须能从流水上直接读出来——这三种混在一起的话，
手动平仓会被读成"跟单逻辑自己平掉了仓位"。

## 10. 工作台实时通道（2026-10-17）

工作台的跟单模块走 `/hubs/followers`（SignalR），与 `/hubs/monitor` 分开：后者的门是「总览」，
这里必须单独校验 `menu:copy-list` 的 `view`。连上以后有两类帧：

| 帧 | 内容 | 前端怎么用 |
|---|---|---|
| `followerChanged(followerId)` | 账本/池快照/配置/实盘账户变了；`0` = 所有跟单员 | 防抖后**静默重取** REST 权威数据，不闪加载态 |
| `marketPrice(marketId, price)` | 一个市场的中间价（`market_stats`） | 只补该市场的标记价，本地重算名义价值、未实现盈亏、ROI、权益与清算价，不打 REST |

行情按市场分组发：连接只收到自己 `SubscribeMarkets` 登记过的市场。分组只决定"谁收得到"，
**上游必须先订 `market_stats/{marketId}`**——这一步在 Hub 的订阅方法里同步做（`IMarketStatsSubscription`，
进程级幂等，协议没有退订帧所以订上就保留）。

账户/流水这类事件只发一句"变了"，数据仍由带同一权限点的 REST 端点返回：
SignalR 里不复制业务查询，也就不存在两份口径。前端断线后由 SignalR 自动重连，
重连时重新登记市场；自动重连耗尽后模块自己每 5 秒再试，页面还开着就不会永远停在"已断开"。
