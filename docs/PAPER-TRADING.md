# PAPER-TRADING.md — 纸面跟单的口径与实现

> 本文件说明「纸面跟单」到底算什么、不算什么，以及每个口径选择背后的理由。
> 代码依据：`src/PoolPilot.Domain/Services/PaperLedger.cs`（会计规则）、
> `src/PoolPilot.Infrastructure/Monitoring/PaperFollower.cs`（驱动与落库）。
>
> **角色划分另见 [LEAD-FOLLOWERS.md](LEAD-FOLLOWERS.md)**：纸面账户现在是「跟单员」的一种模式，
> 它订阅带单员的信号；池子被不被观察由带单员决定，与跟单员的存在无关。

---

## 1. 它解决什么问题

回答一句话：**跟着这个池子做，我的钱会变成多少。**

这与「执行成本测量」（`CopySlippageCalculator` + `copy_fills` 表）是**两件事**，容易混：

| | 纸面跟单（`paper_*` 表） | 执行成本测量（`copy_fills` 表） |
|---|---|---|
| 产出 | 完整账户会计：仓位、盈亏、权益曲线 | 逐腿的摩擦成本（bps） |
| 状态 | 维护仓位账与已实现盈亏 | **不产生任何账户状态** |
| 回答 | 能不能赚 | 每一腿比池子差多少 |
| 依赖 | 池的仓位推送 + 盘口 | 池的成交推送 + 盘口 |

两者都保留，界面分节呈现。只看成本会算不出盈亏，只看盈亏会不知道成本从哪来。

## 2. 规模口径：比例复制

```
规模比例 = 我方本金 / 池子权益
我方目标仓位 = 池子仓位 × 规模比例
本次动作量 = 目标仓位 − 我方现有仓位
```

**为什么必须是这个口径**：止盈止损藏在池子手里，跟单者只能继承它的进出场。
只有等比复制时，"跟它做能不能赚"才有确定答案——我方收益 = 池子收益 − 执行摩擦。

若改成「每个信号固定下 N 单位」，就必须自己发明一套出场规则（池子减仓时我减多少？），
那测的就不再是跟单，而是**自己的策略**。这个区别很关键：
前者是对池子的评价，后者是对自己策略的评价。

### 首次建仓取现价

账户配置后，第一次对账会把仓位一次性对齐到等比目标，**成交价取当时的真实盘口**。
这是真实跟单服务的行为：它按当前市价跟上领单人的现有仓位，而不是假装拿到领单人的开仓价。
所以「我方开仓均价 ≠ 池子开仓均价」是正常的，差额正是后发入场者的真实处境。

### 目标仓位量化到交易所步长

目标数量按 `InstrumentSpec.SizeDecimals` 四舍五入（ENA 是 0.1）。

不做量化会被算术残差毒化：`池仓 × (本金/权益)` 每次重算都可能与上次差 1e-18，
于是每轮对账都会产生一条"低于最小下单量"的假记录，把台账淹掉。
量化不是权宜之计——交易所本来就不接受带小数尾巴的数量。

## 3. 会计规则

| 概念 | 公式 |
|---|---|
| 开仓均价 | 加仓时按数量加权；纯减仓不变；全平归零；反手按本次成交价重开 |
| 已实现盈亏 | `(成交价 − 开仓均价) × 平掉的数量 × sign(原仓位)` |
| 未实现盈亏 | `(盯市中间价 − 开仓均价) × 带符号数量` |
| 账户权益 | `本金 + 已实现 + 未实现 − 手续费` |

**符号由带符号数量承担**（`SignedSize`），多空共用一套公式：
空头数量为负，价格下跌时 `(mark − entry) × 负数` 自动为正。这样不会出现
"只测了多头、空头方向写反"这类只在一半场景暴露的 bug。

**仓位账只由流水重放推出**，不单独持久化一份持仓。这样"持仓与流水对不上"
这种最难查的脏状态在结构上就不可能存在。

**未实现盈亏必须按盘口中间价盯市**，不能用最近成交价：没有成交的市场上成交价是过期的，
会让权益在两次成交之间静止不动，曲线出现假的平台。

## 4. 驱动方式与约束

### 对账跑在心跳上，不挂在推送事件上

仓位频道**只在真正变化时推送**（实测两次变化相隔约 2 分钟，池子不动时一条都不推）。
所以对账由状态心跳（15 秒）驱动——它与上游是否活跃无关，是唯一可靠的驱动源。
一个刚配置好的账户因此能在约 15 秒内完成首次建仓，不必等池子交易。

### 约束与"未跟上"记录

每个动作先过两道交易所约束：最小下单数量、最小下单金额。两者可能同时违反，
此时报告**真正卡住的那个**（把两个约束各自换算成"需要多少本金"，取要求更高者）。

> 实测结论：对现价的 ENA，最小下单金额**永远是硬墙**。
> 判据是 `价格 > 最小金额/最小数量` 即 `0.2447 > 10/35 = 0.2857`，不成立。
> 该结论已固化成断言，ENA 涨过 0.2857 时测试会失败并提醒重新审视。

被跳过的信号**必须记录**（否则账户会显得完美跟踪了池子），但要去重：
键为「市场 + 原因 + 当时的池仓」，池仓一变才记一次，含义是"池子这一动，我没跟上"。

### 跟踪偏差

`跟踪偏差 = 我方持仓 − 等比目标`。它来自被跳过的信号累积，也就是**颗粒度损失**。
本金越接近门槛，偏差越大。这是比盈亏更能说明问题的数字。

## 5. 模式的边界写在界面上，不只写在文档里

导航这一节叫**跟单**而不是"纸面跟单"，因为模式是**跟单的属性**，不是这一节的名字。
新建跟单时可以在「跟单模式」里选：

| 模式 | 状态 | 说明 |
|---|---|---|
| 纸面模式 | 可选（默认） | 不发送任何真实订单，按真实盘口模拟成交并完整记账盈亏 |
| 实盘模式 | **不可选**，界面上写明原因 | 实盘下单需要 API key 对订单签名，而 .NET 与纯 JS 都没有可用的签名器 |

**为什么把不可选项也列出来**：让使用者在界面里就看到边界，
而不是点了半天找不到入口、或从文档里才知道。禁用态旁边直接写出原因，不让人猜。

模式定义集中在 `web/src/domain/copyMode.ts`，界面各处都读它。
接入实盘时**必须改掉这个设计**：模式将不再是前端常量，而是账户的属性、由后端返回——
模式错一次的代价是真金白银，前端常量无法表达"这个账户是纸面、那个是实盘"。

## 6. 刻意不做的（避免误读）

1. **资金费不计入**。持仓跨结算周期会有收付，需要按市场拉资金费历史并按持仓时间积分。
   对"持有数小时"的跟单影响小，但**不是零**，长持仓时会让实际收益低于账面。
2. **不模拟下单被拒**。除了最小数量/金额，交易所还可能因保证金不足、限频等拒绝订单。
3. **不模拟部分成交的风险**。复盘时按盘口实际深度成交（`DepthSufficient=false` 会被标出），
   但真实市价单在快速行情下可能吃得更差。
4. **不追溯池子的既有仓位成本**。见 §2"首次建仓取现价"。
5. **不预测池子的意图**。它打算在哪止损、是否要加仓，都不可能知道——这正是跟单的固有劣势。

## 7. 多账户与驱动

**每个池一个独立账户**，可以同时跟多个池：本金、仓位、盈亏、权益曲线各自记账。
账户以池索引为主键，所以在结构上不可能给同一个池建出两个账户
（同一个池两种本金的历史没有意义，见 §8 关于改本金清空历史）。

驱动分两段，**都是心跳（15 秒）触发**：

| 池的来源 | 快照方式 | 节奏 |
|---|---|---|
| 在 `PoolMonitor:AccountIndexes` 名单内 | WS 推送，快照随时是新的 | 每轮心跳 |
| 连接断开期间 | 主动拉 REST 快照 | `PaperRestReconcileSeconds`（默认 60 秒） |

兜底那一段是必需的：推送不可用时，跟单员会一直静止到重连为止，
而界面上它跟正常运行一模一样。连接正常时它永不触发——
推送始终比 REST 快照新，叠加轮询会让更新的推送被更旧的快照覆盖，凭空造出"平了又开"的动作。

## 8. 数据与运维

- 表：`followers`（本金/模式/开关）、`follower_fills`（含跳过）、`follower_equity_points`（曲线）。
  三者都按**跟单员的自增 Id** 归属，不再借池索引当身份——一个池可以挂多个跟单员。
- 界面：这一节在导航里叫**跟单**（路径 `/copy`）。`/copy` 是**跟单员卡片列表**
  （一屏看完所有跟单的关键数字），点卡片进 `/copy/:id` 看详情。
  卡片刻意不带流水与曲线——把所有账户的完整明细摊在首页，信息量看着大，但要一眼回答的问题反而被淹没。
  旧路径 `/ledger`、`/ledger/:accountIndex` 保留为重定向（这一节原叫「纸面跟单台账」，
  改名不该让已打开的页面与书签失效）。
- **改动本金会清空该账户的流水与曲线**。本金是规模比例的分母，
  两种本金下的流水混在一条曲线里不对应任何真实实验，却会被读成"跟单业绩"。
- 权益点**按事件驱动 + 5 分钟节流**记录（成交时立即记）。按心跳记会一天写 5760 个点，
  其中绝大多数与前一帧只差毫厘，曲线没变细，只是更慢更花。
- 所有时间戳记**我方动作的墙钟时刻**，不记池子快照的时刻——后者在两次推送之间是冻结的，
  会让多个点挤在同一时间戳上，曲线变成一根竖线。

### 建表：`EnsureCreated` 不建新表（已踩过的坑）

`EnsureCreated` 对**已存在**的数据库什么都不做。给模型加新表后，老库永远缺那张表，
接口只报 `no such table`，错误信息完全不提"你需要重建数据库"。纸面跟单的三张表就是这么消失的。

现行做法见 `DatabaseSchemaInitializer`：先 `EnsureCreated`，再让 EF **由模型生成建表脚本**，
只执行库里还没有的对象（表与索引）。脚本来自模型本身，因此不存在手写 DDL 与模型漂移的问题。
**局限**：它只补新对象，**不修改已存在表的结构**——某张表的列变了仍需删库重建。
